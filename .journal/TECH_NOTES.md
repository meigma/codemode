# Technical Notes

- Use hexagonal architecture at all times. Keep business logic isolated from CLI, filesystem, network, storage, and other external adapters.
- Prefer functional testing before calling any feature complete. Unit tests are useful, but they do not prove the tool works the way the design intends.
- Take an agile approach to development. Avoid waterfall: underspecify when useful, prototype early, learn from the result, and refine from working behavior.
- CodeMode authors new code-native MCP servers; it never imports, proxies, translates, or calls downstream MCP servers. The client surface is exactly `search_api`, `describe_api`, and `execute`.
- The secure MVP, source-only repository cutover, and optional Rego authorizer are complete on `master`. The repository ships a Go library, not an executable, binary release, or OCI image.
- The shipped binding matrix is intentionally narrow: non-pointer input structs with required `string` and optional `*int64` fields; non-pointer output structs with `string`, `int64`, `bool`, and `float64` fields.
- A `Builder` is single-threaded and one-shot. It validates every registration before static filtering, compiles binding and namespace data, and returns an immutable concurrency-safe `Server`.
- Stable `CapabilityID` values drive deployment and authorization policy; dotted `CapabilityName` values drive discovery and generated Starlark namespaces.
- Trusted subjects stay in host-owned typed Go context. The `mcpserver.InvocationResolver` runs before every tool operation and must ignore arguments, source, MCP `_meta`, and other client-controlled metadata.
- Canonical keyword binding precedes fail-closed authorization, which precedes every native handler call. Disabled capabilities are absent from discovery, description, generated namespaces, and execution.
- Every execution runs in a fresh re-executed worker process with a restricted Starlark interpreter. Only zero-argument `main()`'s final converted value crosses into MCP; prints, globals, and intermediate expressions do not.
- Deadline or request cancellation kills and reaps the Starlark worker. This process boundary is not complete tenant isolation: CodeMode provides no operating-system CPU, memory, filesystem, or network quotas, and parent Go authorizers and handlers remain cooperative code that must honor context.
- Optional `authz/rego` implements the existing `authz.Authorizer` port with OPA v1.19.1. It accepts trusted in-memory Rego v1 modules, prepares one direct ground Boolean `data` decision before serving, and exposes only `Authorizer`, `New`, and `Authorize`.
- The Rego adapter removes every OPA-declared nondeterministic builtin, keeps `AllowNet` empty, treats builtin errors as fatal, disables print, installs no extension hooks, borrows canonical arguments read-only, and checks context before and after evaluation. These are in-process capability restrictions, not hard isolation.
- Embedded OPA is substantial when imported: session 003's spike observed 126 additional modules, 172 additional compiled non-standard packages, and about 29 MiB of linked binary growth in a minimal comparison.
- The substantive public packages are root `codemode`, `authz`, optional `authz/rego`, and `mcpserver`; internal packages are `internal/binding`, `internal/catalog`, and `internal/execution`, plus generated adapter mocks.
- Generated capability signatures describe invocation syntax only; use `Description.Output` or `describe_api.output` for stable result shapes. MCP output schemas are explicit and non-null, and successful empty collections are normalized to `[]`.
- Trusted direct `authz/rego.Authorize` callers can distinguish undefined and non-Boolean decisions. Root execution projects policy failures to `codemode.ErrPolicyFailure`, and MCP projects them to the fixed `authorization policy failure` text without exposing trusted detail.
- MCP tool descriptions intentionally publish short literal-query discovery, exact-name description, zero-argument `main()`, and bounded recovery guidance. Coarse client errors remain a deliberate non-disclosure boundary.
- `.journal/001/ARCHITECTURE.md` is the settled core architecture; `.journal/001/IMPLEMENTATION_PLAN.md` is complete. Session 002 records the secure MVP, session 003 records the Rego architecture and adapter, and session 004 records the 59-case external functional campaign plus all nine findings-remediation increments.
- Worker-only execution is complete on `master`. Session 006 holds the approved design and five-increment plan; session 008 records implementation through PRs #27–#31. The final host and every test binary that calls `Builder.Build` must call `ServeWorkerAndExit()` before ordinary setup. `Build` performs a fixed five-second same-binary probe; each `Execute` owns one re-executed child; `MaxConcurrentExecutions` defaults to 8; and `MaxValueBytes` independently bounds native arguments, native results, and final values.
- Richer binding/search, observability, fuzzing, benchmarks, and Testcontainers remain evidence-gated. Add them only when observed product needs justify the extra surface.
- OMP 17.3.4 can rewrite model-emitted MCP argument keys and drop unknown fields before dispatch. Treat emitted and dispatched transcript arguments separately; follow upstream issue `can1357/oh-my-pi#9653`. Do not weaken CodeMode schemas to compensate.
- Crossing-value conversion preflights tuple, list, and dictionary lengths against the remaining byte-derived node budget and streams dictionary iteration; PR #26 removed about 64 MiB of avoidable allocation from issue #13's reproduction, and the worker cutover retained those defenses. This is not a hard heap boundary. Issue #23's proposed Go-to-Starlark composite output walker still needs a separate request-scoped intermediate materialization budget rather than silently treating per-crossing `MaxValueBytes` as an aggregate budget.
