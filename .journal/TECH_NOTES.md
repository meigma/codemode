# Technical Notes

- Use hexagonal architecture at all times. Keep business logic isolated from CLI, filesystem, network, storage, and other external adapters.
- Prefer functional testing before calling any feature complete. Unit tests are useful, but they do not prove the tool works the way the design intends.
- Take an agile approach to development. Avoid waterfall: underspecify when useful, prototype early, learn from the result, and refine from working behavior.
- CodeMode authors new code-native MCP servers; it never imports, proxies, translates, or calls downstream MCP servers. The client surface is exactly `search_api`, `describe_api`, and `execute`.
- The secure MVP, source-only repository cutover, and optional Rego authorizer are complete on `master`. The repository ships a Go library, not an executable, binary release, or OCI image.
- Capability inputs use non-pointer structs with required `string`, `int64`, `bool`, and `float64` fields or optional pointers to those four scalar kinds. Omitted optional arguments and explicit Starlark `None` both produce nil pointers and remain absent from canonical authorization maps.
- Capability outputs use compiled structural reflection plans for nested structs, arrays, slices, string-keyed maps, pointers, named scalars, signed and bounded unsigned integers, finite floats, and byte sequences. Discovery remains derived through flat `FieldShape` records with deterministic nested type notation; unsupported or cyclic type graphs and custom marshalers fail registration.
- A `Builder` is single-threaded and one-shot. `Register` compiles and retains valid capabilities while accumulating capability-specific failures; `Build` closes the builder, joins those diagnostics, validates the complete catalog before static filtering, and returns an immutable concurrency-safe `Server`. `Register` panics for nil or already closed builders.
- `CapabilityID` drives deployment and authorization policy and defaults to the dotted `CapabilityName` when omitted. Set an explicit ID before policy or deployment filters must survive a capability rename. An empty capability description defaults to its summary.
- The `mcpserver.InvocationResolver` runs before every tool operation and must ignore arguments, source, MCP `_meta`, and other client-controlled metadata. `StaticSubject` is only for single-user process-owned identity; multi-user hosts authenticate each request, store the trusted identity with `authz.WithSubject`, and use `ContextSubject`.
- `Build` replaces each zero-valued `Limits` field with its bounded `DefaultLimits()` value before validation, so partial overrides do not require restating unrelated budgets; negative signed limits still fail.
- Canonical keyword binding precedes fail-closed authorization, which precedes every native handler call. Disabled capabilities are absent from discovery, description, generated namespaces, and execution.
- Every execution runs in a fresh re-executed worker process with a restricted Starlark interpreter. Only zero-argument `main()`'s final converted value crosses into MCP; prints, globals, and intermediate expressions do not.
- Deadline or request cancellation kills and reaps the Starlark worker. This process boundary is not complete tenant isolation: CodeMode provides no operating-system CPU, memory, filesystem, or network quotas, and parent Go authorizers and handlers remain cooperative code that must honor context.
- Every worker exposes one fixed pure-compute Starlark surface: numeric `sum(iterable)`, `json.decode` / `json.encode` / `json.indent`, and the complete pinned `math` module. Standard universe roots plus `sum`, `json`, and `math` are reserved for capabilities; nested leaves remain legal. Dialect-gated `set` is reserved but unavailable, and there is no built-in `time` module. `MaxExecutionSteps` counts bytecode, not Go builtin internals; issue #45 tracks recursive JSON depth amplification.
- Optional `authz/rego` implements the existing `authz.Authorizer` port with OPA v1.19.1. It accepts trusted in-memory Rego v1 modules, prepares one direct ground Boolean `data` decision before serving, and exposes only `Authorizer`, `New`, and `Authorize`.
- The Rego adapter removes every OPA-declared nondeterministic builtin, keeps `AllowNet` empty, treats builtin errors as fatal, disables print, installs no extension hooks, borrows canonical arguments read-only, and checks context before and after evaluation. These are in-process capability restrictions, not hard isolation.
- Embedded OPA is substantial when imported: session 003's spike observed 126 additional modules, 172 additional compiled non-standard packages, and about 29 MiB of linked binary growth in a minimal comparison.
- The substantive public packages are root `codemode`, `authz`, optional `authz/rego`, and `mcpserver`; internal packages are `internal/binding`, `internal/catalog`, `internal/execution`, `internal/universe`, and `internal/worker`, plus generated adapter mocks.
- Generated capability signatures describe invocation syntax only; use `Description.Output` or `describe_api.output` for stable result shapes. MCP output schemas are explicit and non-null, and successful empty collections are normalized to `[]`.
- Trusted direct `authz/rego.Authorize` callers can distinguish undefined and non-Boolean decisions. Root execution projects policy failures to `codemode.ErrPolicyFailure`, and MCP projects them to the fixed `authorization policy failure` text without exposing trusted detail.
- Capability discovery compiles immutable search documents from enabled names, `SearchTerms`, summaries, and descriptions, then performs a deterministic bounded full-catalog scan. Exact and normalized name matches lead, all required query tokens must meet coverage rules, fuzzy matching is intentionally absent, and `Describe` still requires the exact registered name.
- `Capability.SearchTerms` is discovery-only host metadata: it is neither returned nor callable, but it is inferable through search probing and must not contain credentials, secrets, policy facts, tenant identifiers, or sensitive examples.
- Public search returns `SearchResponse` with non-nil `Results` and `Truncated`; MCP implementation version `2` exposes the same required object. Registration count, searchable metadata, raw query bytes, result count, and structured response bytes are bounded; JSON-RPC framing and the SDK text mirror sit outside the internal response cap.
- MCP errors retain stable coarse prefixes. Only direct ordinary parser or resolver diagnostics and child-origin binding diagnostics may add model-derived detail; worker frames allow that detail only for `invalid_program` and `invalid_arguments` with a fixed 4 KiB cap. Root `Error()` text stays coarse, and MCP alone formats the suffix. Never expose `starlark.EvalError.Msg`, parser panic-recovery text, call stacks, handler or policy messages, panic values, protocol errors, or internal causes.
- Docs use canonical wording: "worker process" on first mention then "worker"; "native call"; "top-level source loading"; only `main`'s final converted value is *exposed to the caller* (native arguments and results still cross the private worker protocol); `MaxExecutionTime` covers slot wait through parent dispatch with kill/reap overhead outside the budget. Reuse these sentences; do not paraphrase them into new drift.
- Docs publishing exact expected outputs must be executed reader-style from the doc text alone; source-grounded review alone passed an unreproducible procedure in session 009. Any PR that rewrites the tutorial must functionally re-verify every how-to that starts "from the tutorial" — #34 orphaned the Rego guide's verification this way.
- `.journal/001/ARCHITECTURE.md` is the settled core architecture; `.journal/001/IMPLEMENTATION_PLAN.md` is complete. Session 002 records the secure MVP, session 003 records the Rego architecture and adapter, and session 004 records the 59-case external functional campaign plus all nine findings-remediation increments.
- Worker-only execution is complete on `master`. Session 006 holds the approved design and five-increment plan; session 008 records implementation through PRs #27–#31. The final host and every test binary that calls `Builder.Build` must call `ServeWorkerAndExit()` before ordinary setup. `Build` performs a fixed five-second same-binary probe; each `Execute` owns one re-executed child; `MaxConcurrentExecutions` defaults to 8; and `MaxValueBytes` independently bounds native arguments, native results, and final values.
- Composite inputs, observability, fuzzing, benchmarks, and Testcontainers remain evidence-gated. Add them only when observed product needs justify the extra surface.
- OMP 17.3.4 can rewrite model-emitted MCP argument keys and drop unknown fields before dispatch. Treat emitted and dispatched transcript arguments separately; follow upstream issue `can1357/oh-my-pi#9653`. Do not weaken CodeMode schemas to compensate.
- Crossing-value conversion preflights container lengths against byte-derived node budgets before proportional allocation. `MaxValueBytes` independently bounds each native argument, native result, and final value; `MaxIntermediateValueBytes` defaults to 8 MiB and separately bounds the cumulative encoded bodies of successful native results within one `Execute`. PR #26 removed the oversized final-conversion allocation from issue #13, and session 011's PRs #35–#39 implemented the composite binding and aggregate-budget design that closed issue #23.
