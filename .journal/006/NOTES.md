## 2026-08-24 12:27 — Kickoff
Goal for the session: Review GitHub issue #12 about monolithic Starlark built-ins overrunning `MaxExecutionTime` and propose a correct remediation.
Current state of the world: CodeMode runs Starlark in-process with cooperative thread cancellation, documents in-process budgets rather than hard tenant isolation, and has not implemented worker-process containment.
Plan: Inspect the live issue and current execution path, reproduce and measure the deadline overrun, evaluate remediation boundaries, and propose a focused fix with verification criteria.

## 2026-08-24 12:32 — Issue review
Reviewed issue #12 and reproduced it through the public `Server.Execute` API on `master` commit `ccac0332a64c52530ebf0102849f73eecf867a12`. With a 1 ms budget, `list(range(8000000))` completed after 25.7–30.8 ms, `tuple(range(8000000))` after 26.5–27.4 ms, and `list.extend(range(8000000))` after 143.5–157.0 ms; every call then returned `ErrResourceLimit` wrapping `context.DeadlineExceeded`.

Starlark-Go checks `Thread.Cancel` between interpreter bytecode operations, not while standard Go built-ins run. The current dependency has multiple unmetered allocation and iteration paths beyond `list`, including `tuple`, `enumerate`, `reversed`, `set`, `sorted`, `zip`, and list methods. Upstream maintainers explicitly recommend a separate OS process for hostile scripts.

Decision: treat the issue as valid CWE-400. Correct the in-process contract and regression coverage immediately, but do not claim that shadowing selected built-ins closes the availability boundary. Hard closure requires host-level worker process or container isolation with a parent-enforced deadline, memory/CPU controls, bounded concurrency, and worker termination. CodeMode cannot transparently move the current in-memory Go handler and authorizer callbacks across a process boundary, so the isolated execution mode needs an explicit host/worker protocol and should be proven in a disposable spike before public API design.

## 2026-08-24 12:40 — Re-exec worker split decision
Settled the multi-process shape with the developer: one binary, Docker-style re-exec (`os.Executable()` + env marker + inherited pipe FDs). The host branches in `main`: build the server with the identical wiring, then `codemode.IsWorker()` → `codemode.ServeWorker(server)` instead of normal serving. Shared wiring means the child rebuilds the real catalog and binding plans without registration serialization.
Chosen cut: interpreter-only child (Cut B). Child runs the fresh Starlark thread, step and source limits, and namespace stubs; every native call is forwarded to the parent as (capability ID, canonical JSON args). Parent re-binds, authorizes, dispatches handlers, and returns converted JSON. Child never sees subject, authorizer, or credentials. Rejected Cut A (whole execution in child) because it moves trusted handlers, credentials, and Rego into the killable sandbox and couples the memory cap to handler workloads.
Wire format falls out of existing design: binding already canonicalizes native arguments to JSON-shaped maps before authorization and converts outputs to JSON-shaped values, so frames are length-prefixed JSON of data we already construct. Parent treats the child as untrusted after spawn: bounded pipe reads, frame validation, re-binding, protocol violation → kill + ErrInternal. Deadline path is SIGKILL of the process group with no graceful-cancel protocol; Execute then promises MaxExecutionTime plus bounded kill/reap overhead.
Open wrinkles for the spike: host build functions that eagerly dial dependencies pay per-child cost and leak credentials into the sandbox (document lazy init; maybe a plans-only worker build later); hard memory caps are Linux/cgroup-grade only (macOS dev-grade, Windows deferred; v1 scoped to Unix setpgid/kill(-pgid)); fresh child per execution, no pooling until spawn cost is measured to matter; isolation stays opt-in with in-process default.
Next step: disposable spike proving same-binary re-exec, pipe frames, one forwarded native call, and kill-at-deadline against the issue #12 payload, measuring overrun and spawn overhead.

## 2026-08-24 12:47 — Worker-only decision
Correction to 12:40: isolation is no longer opt-in. With zero consumers pre-1.0, the developer challenged the dual-mode surface; decided worker-only public `Execute`. Rationale: adding an unsafe in-process escape hatch later is additive, removing a public mode later is breaking; one public contract for `MaxExecutionTime` (near-hard: deadline plus bounded kill/reap overhead); the security-critical path becomes the only exercised path. The in-process engine stays in `internal/execution` unchanged — it is what runs inside the child — so this removes a public contract, not an engine.
Accepted costs and mitigations: mandatory `IsWorker`/`ServeWorker` branch in every host `main` (and consumer `TestMain`), mitigated by a `Build()`-time probe spawn/handshake that fails startup on missing wiring; fork-bomb guard — `Execute` observing the worker marker refuses to spawn and errors; plans-only worker build (child gets binding plans and namespaces, never handlers or authorizer) promoted from later-maybe into spike scope so every host avoids per-child dependency dials and credentials never enter the sandbox.
Platform re-examination: under Cut B the child spawns nothing, so plain `child.Kill()` suffices on all platforms; process-group kill is defense in depth, not a Unix prerequisite. Only the hard memory cap remains Linux/cgroup-grade. This weakened the strongest argument for an in-process fallback.
Spike gate extended: prove the probe handshake and the `TestMain` ergonomics in addition to re-exec, frames, one forwarded native call, and kill-at-deadline against the issue #12 payload. If ergonomics are ugly, the evidence defines the shape of a loudly-named unsafe escape hatch; otherwise worker-only ships.

## 2026-08-24 12:55 — Worker spike executed, all gates pass
Ran the disposable spike in `/tmp/codemode-worker-spike`; evidence recorded in `WORKER_SPIKE.md`. All seven gates passed: same-binary re-exec, framed pipes with a 1 MiB read cap, native call forwarded to a parent-side handler (proven by pid), kill-at-deadline, probe handshake, fork-bomb guard, and the `TestMain` branch (8 lines, `go test` and `-race` clean).
Numbers: probe/spawn median 2.51 ms; trivial execution end-to-end median 2.33 ms; the issue #12 payloads under a 1 ms deadline were killed with a 1.22–1.35 ms window (1.2–1.3x) versus 25.7–157.0x in-process. Kill+timer overhead ~0.3 ms absolute — noise against the 5 s default budget. Fresh-child-per-execution is viable without pooling.
Learnings feeding the real design: the child ran with no handlers/authorizer at all, confirming the plans-only worker build; JSON round trip erased int64 to float64, so the real protocol needs a numeric encoding decision (json.Number or typed envelope); plain `Process.Kill` sufficed since the child spawns nothing; the reader goroutine needs deterministic shutdown; worker stderr policy must be chosen. Not exercised: cgroup memory caps, concurrency semaphore, Windows, MCP integration.
Verdict: worker-only ships. Ergonomics are fine; no unsafe escape hatch needed on current evidence.
